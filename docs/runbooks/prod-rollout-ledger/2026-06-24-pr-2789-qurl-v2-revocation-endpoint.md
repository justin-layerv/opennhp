# 2026-06-24 · PR #2789 · qURL v2 revocation endpoint + AC fanout (P4e Slice 2)

- **Owner:** prod rollout coordinator
- **Source:** [#2789](https://github.com/layervai/nhp/pull/2789) · receive side for [#2787](https://github.com/layervai/nhp/pull/2787) (Slice 1) · cross-repo with qurl-service NHP Sink (P4e Slice 6/7) · follow-up [#2790](https://github.com/layervai/nhp/issues/2790)

Adds `POST /nhp/internal/revocation` (VPC-only, HMAC via `NHP_INTERNAL_AUTH_SECRET`, tri-mode auth like `/nhp/internal/knock`) and fans revocation events out to connected ACs as `NHP_REV`. Slice 1 (#2787) explicitly deferred the secret-sync + send-before-revoke ordering to this slice. No live sender until the qurl-service NHP Sink (Slice 6/7) is deployed and wired into the revoke path; the endpoint is inert until then.

- [ ] Cross-repo: confirm prod qurl-service tasks and prod NHP server instances read the SAME `NHP_INTERNAL_AUTH_SECRET` parameter before qurl-service starts signing revocation POSTs (same secret already used by `/nhp/internal/knock` — verify the revocation Sink reads it too). Coordinate so the **send side is live and signing before any customer revoke can fire**, and keep nhp internal-auth in permit mode until `InternalAuthSuccess` is observed for the revocation path.
- [ ] Pre-rollout (HARD, security — before the qurl-service revoke Sink goes live AND before v2 admission is enabled in any live env): re-confirm the qurl-service **no-positive-cache deny-re-admission** contract still holds — a revoked qURL/resource is denied on its very next admission with no stale-cache window. The AC's pre-epoch revoke gate (`admitEpoch`, [#2781](https://github.com/layervai/nhp/issues/2781)) can revoke-APPLY a `(scope, scope_key)` only ONCE until real per-`(scope,scope_key)` monotonic epochs land ([qurl-service#1010](https://github.com/layervai/qurl-service/issues/1010)), so this contract is the sole guard that a revoked-then-re-admitted key (resource scope is the sharp case) cannot survive to natural expiry. Verified 2026-06-30 at qurl-service `internal/service/resolve_service.go` (`!resource.IsActive()` → `ErrResourceRevoked`; `QurlStatusRevoked` → `ErrQurlRevoked`; v2 disables the qurl-router L7 positive-auth cache). Re-verify if the qurl-service admission path changed since.
- [ ] Rollout: keep qurl-service emitting **cell-wide** fanout for the initial rollout (targeted fanout is gated on #2790 — `target_ac_ids`↔`ACConn.ACId` correspondence must be proven end-to-end, and the `revocation-targeted-zero-match` alarm must be applied and not ALARM before enable). Do not enable targeted cross-repo in this rollout.
- [ ] Post-rollout: run a prod revoke smoke (revoke a throwaway qURL/resource via qurl-service) and confirm `RevocationReceived > 0`, `RevocationFanoutSent > 0`, and `RevocationFanoutBackpressure = 0` on the prod NHP server; confirm the AC tears down the live entry (or the entry expires within SLO if no live flow). Confirm `InternalAuthFailStrict = 0` / `InternalAuthFailPermit = 0` for the revocation path before any strict flip.
- [ ] Post-rollout: watch `RevocationFanoutBackpressure` — a sustained nonzero value means the shared send queue is saturated and revocations are being deferred to qurl-service retry; page and investigate send-pipeline pressure (a revoke is security-relevant and the retry budget is finite).
- [ ] Rollback: revocation delivery is best-effort and fail-open by design (a lost `NHP_REV` leaves the entry to expiry), so disabling is low-risk: stop qurl-service from publishing revocation events (revert the Sink wiring) — the nhp endpoint then receives nothing and needs no nhp-side change. The route itself can stay deployed (inert without a sender).
