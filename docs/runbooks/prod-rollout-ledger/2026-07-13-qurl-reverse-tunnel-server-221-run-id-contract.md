# 2026-07-13 · qurl-reverse-tunnel-server #221 · Token RunID binding

- **Owner:** prod rollout coordinator
- **Source:** [NHP #3224](https://github.com/layervai/nhp/pull/3224), [NHP #3226](https://github.com/layervai/nhp/issues/3226), [qurl-conformance #25](https://github.com/layervai/qurl-conformance/issues/25), [qurl-go #65](https://github.com/layervai/qurl-go/issues/65), [qURL Connector #424](https://github.com/layervai/qurl-connector/issues/424), [qurl-reverse-tunnel-server #221](https://github.com/layervai/qurl-reverse-tunnel-server/pull/221)

This PR is validator enforcement, not producer activation. It can deploy independently while current ACK entries have empty stored RunIDs. The request field remains optional only for those entries; once #3226 stores a binding, NHP rejects both omission and inequality as `run_id_mismatch`. An authenticated internal caller holding the shared HMAC secret can therefore observe whether a live entry has a binding by omitting `agent_run_id`; this deliberate one-bit distinction never discloses the value, and `/nhp/internal/token/validate` must remain inside that authenticated trust boundary. Customer activation requires one canonical RunID to be established before the knock and remain byte-identical through authenticated KNK, ACK storage, validator request/response, first FRP Login, and SessionStore. There is no server-autogenerated compatibility phase.

- [ ] Pre-rollout: deploy this NHP change to sandbox and verify current entries with an empty stored RunID remain `valid=true`; verify a synthetic non-empty stored RunID returns signed HTTP 200 with `valid=false`, `error=run_id_mismatch`, and no source/user/owner/expiry metadata when the request RunID is either omitted or different. A different request echoes its RunID; omission leaves `run_id` absent.
- [ ] Validator rollout: deploy NHP #3224 to production first and record the exact image. Do not treat a zero mismatch rate as binding proof while ACK entries still store empty RunIDs; it only shows that the enforcement branch is dormant.
- [ ] Alert-delivery gate: before #3226 activates stored RunIDs, use the sandbox synthetic mismatch to prove the dedicated 60-second alarm enters `ALARM`, the notification reaches the intended sandbox SNS sink, and the alarm returns to `OK` after the metric becomes absent. Do not inject a synthetic mismatch into production.
- [ ] Pre-knock producer gate: complete NHP #3226, qurl-conformance #25, and qurl-go #65 so the authenticated KNK field and local/shared ACK writers preserve the pre-knock canonical RunID exactly. qurl-go owns `NewCycleRunID` / `ValidateCycleRunID` (8 cryptorandom bytes encoded as exactly 16 lowercase hex characters) and requires explicit `NativeKnockOptions.RunID`; `Knock` never generates implicitly. Extend the existing application-body vectors rather than duplicating full packets: pin exact body bytes and reject duplicate/alias keys, whitespace, uppercase, 15/17-character, and non-hex values. The generic NHP parser permits missing/empty only for explicit legacy paths, while the native Connector API rejects both before network action.
- [ ] First-Login seed gate: complete qURL Connector #424 through a supported released FRP client API (or an explicitly reviewed LayerV fork), then prove the connector calls qurl-go's generator once per outer knock/service cycle, owns reuse across retries/reconnects, and supplies the result unchanged to both `NativeKnockOptions.RunID` and FRP's first Login. Reflection, `unsafe`, log scraping, response inference, and mutation after the knock are forbidden.
- [ ] Consumer gate: qurl-reverse-tunnel-server #221 may merge as a preparatory supplied-only guard, but do not deploy that final contract until the producer and seed gates are ready. It must require the Login's supplied canonical non-empty `agent_run_id`, reject missing/noncanonical input before the validator RPC, and accept `valid=true` only with an exact non-empty echo. Remove the fresh-Login server-autogeneration accepted path. Only the additional `knock_token_run_id_mismatch` telemetry is log-only; Login rejection remains fail closed.
- [ ] Hard activation-order gate: artifacts may be staged earlier, but do not let #3226 write the first non-empty stored RunID until the upgraded Connector supplies the same canonical value in authenticated KNK and first Login and #221's required-and-exact assertion path is live. Reversing this order makes every omitted `agent_run_id` a hard Login failure, not a tolerated drift sample. Inventory every authenticated caller of `/nhp/internal/token/validate`; any caller other than qurl-reverse-tunnel-server must also prove mandatory canonical RunID assertion before activation.
- [ ] Activation proof: before enabling customers, exercise exact match, omission, and mismatch end to end across connector generation, authenticated KNK, local/shared ACK metadata, signed validator request/response, first and reconnect FRP Login, and SessionStore. A new outer cycle gets a new RunID; retries/reconnects inside one cycle reuse it.
- [ ] Post-activation: confirm the dedicated 60-second `InternalTokenValidateFailure{Reason=run_id_mismatch}` zero-tolerance alarm remains OK during canary and burn-in. Any nonzero sample is producer/consumer contract drift and blocks rollout completion; do not rely only on the aggregate failure alarm.
- [ ] Rollback: before activation, revert only the component that introduced the defect; empty stored-RunID entries remain compatible with #3224. After activation, stop customer rollout and roll back the connector/qurl-reverse-tunnel-server producer-consumer path before considering an authorized NHP rollback. Reverting NHP alone cannot restore Logins because #221 independently rejects missing or non-exact validator echoes, and silently re-enabling server autogeneration is not an allowed availability fallback.
