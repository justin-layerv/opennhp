NHP-AC Customer Enforces access rules via iptables/eBPF, deployed in customer VPC
Agent End User Initiates NHP knock from user device (laptop, mobile)

2. Multi-Tenancy Requirements

2.1 Current State

Current limitation: NHP Server operates in a flat namespace. OrganizationId exists in the protocol but is metadata only - not used for routing or isolation.

2.2 Required Changes

Tenant Router (New Component)

type TenantRouter struct {
    configStore  ConfigStore           // etcd or similar
    tenantCache  map[string]*TenantConfig
    cacheMutex   sync.RWMutex
}

func (r *TenantRouter) GetTenantConfig(orgId string) (*TenantConfig, error) {
    // 1. Check cache
    // 2. If miss, fetch from configStore
    // 3. Validate tenant is active
    // 4. Return tenant-specific config
}

Files Requiring Modification

File Changes Required
endpoints/server/config.go Add TenantRouter, ConfigStore interface
endpoints/server/udpserver.go Route by OrganizationId before processing
endpoints/server/msghandler.go Pass tenant context through handlers
endpoints/server/tokenstore.go Namespace tokens by tenant
New: tenant.go TenantRouter, TenantConfig, TenantCache
New: configstore.go ConfigStore interface, etcd implementation

4.2 Customer Onboarding Flow

1. Subscribe to SaaS

Customer subscribes to LayerV NHP on AWS Marketplace

2. Tenant Provisioned

LayerV auto-provisions: OrganizationId, API key, tenant config in etcd

3. Deploy AC

Customer launches CloudFormation with OrganizationId + API key

4. Configure Resources

Customer defines protected resources via LayerV console

5. Deploy Agents

End users install agents from LayerV portal (Windows, macOS, Linux, iOS, Android)
