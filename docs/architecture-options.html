NHP Architecture Options

Where Should the Access Controller (AC) Live?
Architecture Discussion Document | December 2024

The Core Question

Decision Required

Should the NHP Access Controller (AC) be deployed in:

  1. Customer VPC - Customer deploys and manages AC
  2. LayerV VPC - We manage AC, customer just whitelists our IPs

This decision fundamentally changes:

  • Customer onboarding complexity
  • Data plane traffic flow
  • Security and compliance posture
  • Operational responsibility
  • Cost structure

Control Plane

Agent → LayerV Server → Customer AC

Authentication, authorization, policy decisions

Data Plane

Agent → Customer Resource

Direct connection, never touches LayerV

How AC Works

The AC doesn't proxy traffic. It controls access by dynamically managing firewall rules:

# When user is authorized, AC runs:
iptables -A INPUT -s {agent_ip} -d {resource_ip} -p tcp --dport 5432 -j ACCEPT

# When session expires:
iptables -D INPUT -s {agent_ip} -d {resource_ip} -p tcp --dport 5432 -j ACCEPT

Pros

  • Data never leaves customer VPC
  • Full compliance (HIPAA, PCI, etc.)
  • Low latency (direct connection)
  • Customer pays bandwidth
  • Resources stay truly private
  • No IP whitelist management

Cons

  • Customer must deploy AC
  • More complex onboarding
  • Customer manages AC updates
  • Need CloudFormation/Terraform
  • Customer needs AWS expertise

Key Change: AC becomes a proxy/gateway, not a firewall controller. Customer exposes resources with IP whitelist.

Customer Requirements

# Customer must whitelist LayerV AC IPs:
# AWS Security Group or iptables:
Allow 52.1.2.3/32 → Resource:5432
Allow 52.1.2.4/32 → Resource:5432

# Resource needs to be reachable from internet (public IP or NAT)

Pros

  • Zero customer deployment
  • Simplest onboarding
  • LayerV controls all updates
  • No AWS expertise needed
  • Works with any cloud/on-prem

Cons

  • Data transits LayerV (compliance issue)
  • Resource must be publicly reachable
  • Higher latency (extra hop)
  • LayerV pays bandwidth
  • IP whitelist management
  • "Expose to internet" = security concern

Hybrid Options

C Connector Pattern (Cloudflare/Zscaler Model)

Customer deploys a lightweight "connector" that dials OUT to LayerV. No inbound firewall rules needed.

The Hard Truth

Option B (AC in LayerV VPC) requires customers to expose resources to the internet.

Even with IP whitelisting, security teams often reject this. "Publicly reachable" is a red flag in audits.

What We're Really Asking

Option A/D: "Deploy our software"

Customer runs AC in their VPC. Resources stay private. Data never leaves.

Customer reaction: "Makes sense for Zero Trust"

Option B: "Expose your database to the internet"

Put a public IP on your database. Whitelist our IPs. Trust us.

Customer reaction: "Absolutely not"

Why Connector (Option C) is the Compromise

If we want minimal customer deployment WITHOUT exposing resources:

  • Customer runs a tiny connector (outbound-only, no firewall changes)
  • Connector establishes tunnel to LayerV
  • Traffic flows through tunnel, resources stay private
  • This is exactly what Cloudflare, Zscaler, and Tailscale do
Trade-off: "Nothing to deploy" (Option B) only works if customers accept public exposure. Most won't. The realistic "simple" option is a lightweight connector (Option C).

Suggested Path Forward

  1. Launch with Option A (AC in customer VPC via CloudFormation) - already built
  2. Add Option C (Connector) for customers who want simpler deployment
  3. Add Option D (PrivateLink) for enterprise tier
  4. Skip Option B - the "no deployment" benefit doesn't outweigh the security objections

Discussion Questions

For the Architecture Team

  1. Are we comfortable with data plane traffic transiting LayerV infrastructure? (Options B, C)
  2. What's our bandwidth cost tolerance if traffic flows through us?
  3. Do we want to build a Connector pattern (Option C), or focus on CloudFormation/Terraform for Option A?
  4. Which customer segments are we targeting first? (This drives priority)
  5. Is the "zero deployment" goal worth the security objections it will raise?

Technical Questions

  1. If we go with Connector (Option C), what protocol? WireGuard? WebSocket? QUIC?
  2. How do we handle connector HA/failover?
  3. What's the minimum connector footprint? (Docker? Single binary?)
  4. Can we make Option A simpler with a one-line install script?
